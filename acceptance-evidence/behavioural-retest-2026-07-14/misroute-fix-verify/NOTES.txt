2. CORRECTED MECHANISM (the SCORECARD's claim was wrong on TWO points)
────────────────────────────────────────────────────────────────────────
SCORECARD claimed: the classifier misrouted to the analysis-EXPLANATION
handler (explain_results), which dead-ended on the no-analysis precondition,
and "llm_calls: [] — the model was never invoked".

Both are refuted by the evidence:

(a) THE MODEL WAS INVOKED.  `_diagnostic_trace.llm_calls` is populated ONLY
    on the draft_graph exit path (see T0, which shows the real draft LLM
    call).  For turn_executor exits, route-v2.ts builds a MINIMAL trace
    (buildMinimalV5DiagnosticTrace) WITHOUT threading turnTimings
    (route-v2.ts ~line 424), so llm_calls is STRUCTURALLY ALWAYS [] and
    substage_timings is always just {finalisation_ms} — regardless of
    whether the router ran.  So llm_calls:[] proves nothing here.  The ~30s
    latency on T1/T2 (vs the 2.2s purely-deterministic T3 guard) shows the
    routing + coach/converse LLM DID run.

(b) IT WAS NOT the explain_results handler.  That handler's precondition
    chip is chip_action_run_analysis (executableChip → "Run analysis").
    T1/T2 carried chip_action_rerun_analysis / "Re-run analysis" /
    "Re-run the analysis." — which is RERUN_ACTION, emitted ONLY by
    buildCoachingDegradeResponse (coaching-output-postcheck).

Actual mechanism: the router returned a coach/converse turn, the LLM
produced a genuine coaching answer, and then the COACHING-OUTPUT
POST-CHECK degraded it to the canned "no analysis" nudge —
  turn-executor.ts applyCoachingOutputGuard (~L969, called at L6738/L6865)
  -> checkCoachingOutput() fired a STATE-CONDITIONAL violation
     (confident_advice_under_unsafe_state / stale_presented_as_fresh)
     purely because freshness === 'none' (isStateUnsafe true pre-analysis)
  -> buildCoachingDegradeResponse() (coaching-output-postcheck.ts:672-692)
     -> buildAnalysisAbsentTemplate + RERUN_ACTION.
The user's real coaching answer was thrown away.  This is proven end-to-end
with a mocked router in
  src/orchestrator-v5/__tests__/turn-executor-coaching-postcheck.integration.test.ts
(the pre-fix version asserted exactly this degrade under freshness 'none').

────────────────────────────────────────────────────────────────────────
3. THE FIX (minimal; src/orchestrator-v5/coaching/coaching-output-postcheck.ts)
────────────────────────────────────────────────────────────────────────
The state-conditional rules exist to stop the model presenting an EXISTING
analysis RESULT (stale / unknown / blocked / unusable) as if it were
current.  Pre-analysis there is NO result to misrepresent, so they were
mis-firing on ordinary coaching that weighs options or echoes the user's own
numbers.  Gate them on a result actually existing:

    const analysisResultExists = pack.analysis_present && pack.freshness !== 'none';
    if (analysisResultExists && isStateUnsafe(pack)) { ...directional/result rules... }

Preserved:
  - ALL always-unsafe rules still fire pre-analysis (internal-field exposure,
    invented mutation-success, value-change narration, unsupported
    evidence/confidence claims) — a fabricated CLAIM is still caught.
  - Post-analysis stale/unknown/blocked/unusable directional-advice and
    result-presentation degrades are UNCHANGED (unit tests still green).
  - The legitimate "you asked to explain an analysis that hasn't run yet"
    nudge is a DIFFERENT code path (explain_results handler / no-analysis
    guard) and is untouched.

5. REVIEW R2 HARDENING (second adversarial pass — same PR #450)
────────────────────────────────────────────────────────────────────────
The #450 narrowing (gate the state rules on a result existing) was correct
but opened / left three gaps, all closed here:

(1) GATE FIX — coaching-output-postcheck.ts checkCoachingOutput:
    `if ((analysisResultExists || pack.blocked) && isStateUnsafe(pack))`.
    The bare `analysis_present && freshness!=='none'` gate ALSO disarmed the
    state rules for a FAILED-run / FACT-LOSS blocked state (analysis_present
    false but the scenario/UI still asserts an unusable result). `|| pack.blocked`
    restores that protection. T1/T2 unaffected (blocked is false there).
    New fixture BLOCKED_NO_FACT (analysis_present:false, blocked:true) +
    directional advice → still degrades (was shipping pre-fix).

(2) NEW ALWAYS-ON RULE `fabricated_result_reference` — fires only pre-analysis
    (`!analysisResultExists`). Attribution-anchored; does NOT match a bare `%`
    (user-echoed "your ~3% churn" ships). Four regexes:
      (a) (analysis|results|simulation|monte carlo)+(shows|says|found|indicates|
          points to|came out|reveals)
      (b) (according to|based on) the (analysis|results|simulation)
      (c) (I|we) ran the (analysis|simulation|numbers)      [invented run]
      (d) \d{1,3}% (probability|chance|likelihood)  OR  wins with \d{1,3}%
    Accepted phase-② misses (documented in PR): "your model shows X wins"
    ('model' collides with legit structure talk) and a bare "higher expected
    value" (no attribution anchor).

(3) FALSE-STALENESS FIX — route-with-tool-use.ts COACHING_CONTEXT_INSTRUCTION.
    The single unsafe-state bullet told the model (for freshness 'none' too) to
    say the results "may be out of date" and suggest "re-running" — FALSE
    pre-analysis and a live partial-recurrence of T1/T2 (model self-nudges).
    Split into an honest 'none' bullet ("no analysis has been run yet …", no
    "out of date"/"re-run") + the retained "Otherwise …" bullet for genuinely
    stale/unusable results. The "don't recommend one option before analysis"
    stance is intentionally retained (phase-② design question).
